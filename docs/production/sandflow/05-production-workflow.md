# Sandflow / Sand3D — 05 Recommended Production Workflow (conditional)

**Precondition:** this workflow is justified **only for the asset categories that passed the
evaluation** (hard-surface mechanical/architectural props — see 06). It is deliberately
*not* implemented as permanent infrastructure: adopting it means moving these directories
out of `tools3d/sandflow_eval/` and ratifying the conventions below. Nothing in the game
depends on any of it.

## 1. Pipeline

```
sand3d program (tools3d/sandflow/programs/<id>.py)
  → s3d.export .glb (metres, Y-up, rest pose, joint extras)
  → [optional Blender pass: UV+bake/decimate/name cleanup — only when an asset needs maps or edits]
  → validate (build-manifest QA gate + glb validator + tsc/vitest)
  → human visual approval (renders + in-engine showcase)
  → copy to web-three/public/models/<slot>.glb   ← the only production touchpoint
  → wire through the existing seam (registerGlbProp / upgradePropWithGLB / FURNITURE_SLOTS)
```

Sand3D stays **build-time only**. The game must keep working with the venv deleted — same law
as `tools3d/` today ("the GLB is a costume, never a dependency").

## 2. Where things live

| path | contents |
|---|---|
| `tools3d/sandflow/programs/` | source of truth: one `<asset_id>.py` per asset + `_nyc.py` palette |
| `tools3d/sandflow/renders/` | preview renders (approval evidence), regenerated by `render_previews.py` |
| `tools3d/sandflow/validation/` | `build-manifest.json`, `glb-validation.json`, determinism hashes |
| `web-three/public/models-experimental/` | staging GLBs (dev-only; never referenced by shipped scenes) |
| `web-three/public/models/` | **approved** production GLBs only (existing convention) |
| `docs/production/sandflow/ASSET-LICENSES.md` | per-asset provenance record (created at adoption) |

## 3. Conventions (distilled from the evaluation's iteration log, 03 §9)

**Naming**
* Asset id / file / GLB scene root: `snake_case`, matching the game's semantic slot ids
  (`hydrant.glb`, `apartment_door.glb`).
* Nodes: the sand3d part names (`leaf_slab`, `door_ring`); groups for mechanisms
  (`washer_door`); joints `<part>_<motion>` (`door_hinge`, `drawer_slide`) — these names reach
  the GLB and are what three.js code should key on (or better: key on `s3d_joint` extras).
* Materials are auto-named by preset (`painted_metal color="#2b4a3e"`); normalize in the
  Blender pass only if an asset ships with textures.

**Program style** (already the repo's guidelines, now proven on NYC props)
* Head function = table of contents; one function per part; cut before place; face-frame `y`
  is up with origin at the foot; `grid()` is centred; `box()` starts at z=0; parts positionally
  into `assembly`, frames only as anchors; fronts at Blender −Y; build at rest (no `pose` in
  the shipped program — `*_open()` variants are for documentation renders only).

**Export**
* One GLB per asset: metres, Y-up, origin at footprint base-centre, rest pose.
* Joints carry `s3d_joint` extras — the runtime contract; do not post-process them away.
* Poly budget guidance from measurements: ≤ 16k tris for hero props, ≤ 8k for repeated street
  furniture, and prefer ≥ 500 mm cylinders (the fixed chord law) — or accept the segment cap.

**Validation gate (all must pass before an asset moves to production)**
1. `run_all.py --only <id>` prints `REPORT OK` with dims inside ±5% of the spec table.
2. `validate_glb.py`: 0 degenerate tris, ground-seated bbox, joints schema intact.
3. Determinism: rebuild SHA-256 match (once per program, and on sand3d/bpy version bumps).
4. In-engine: loads in `?showcase=sandflow`, materials/shadows correct, joint (if any) poses
   from extras; `tsc --noEmit` + `vitest run` green.

**Human visual approval**
* Per-asset: render contact sheet + one in-engine screenshot attached to the PR that promotes
  the GLB to `public/models/`. The showcase is the review tool; keep it maintained.

**Licensing records** (per asset, in `ASSET-LICENSES.md`)
* Author, date, source program (original / adapted-from with license notice), any reference
  sources, and the final SHA-256. Apache-2.0 (sand3d, and any adapted example programs like
  `washing_machine.py`) requires retaining notices — the record is where they live.
* **HF dataset programs**: never ship without the per-row attribution workflow (dual license
  layers, per 01 §4). Treat dataset mining as a separate, explicit decision.

**Reproducibility**
* `requirements-sand3d.txt` pins sand3d+bpy; bump sand3d/bpy only with a full-pack rebuild +
  SHA comparison (the determinism check makes version drift visible immediately).
* Every program is rebuildable with one command; GLBs in production are *build artifacts* —
  the program is the asset.

## 4. Scaling opinion (dozens → hundreds of assets)

The economics that made the 12-asset pack fast hold at scale: ~0.1–1.2 s build per asset,
seconds to restyle (change 3 numbers), free variants. What does not scale without care:
per-asset draw calls (mitigate: `mergeGltfParts` + `InstancedMesh`, both measured in 04) and
texture-driven realism (mitigate: the optional Blender bake pass). A 100-asset Alder Heights
street pack is a realistic target for this pipeline; a 100-asset *hero* pack is not.
